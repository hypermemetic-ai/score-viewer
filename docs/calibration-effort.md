# Alternating effort evidence

The new viewer collection stores `calibration-effort-v2.json`, archive identity `viewer-calibration-effort-v2`, with protocol identity `viewer-combined-alternating-effort-v2`. The task is **press both keys together, then alternate**. The alternating trill releases each finger between its turns. Grades 0–3 report both combined pressing and an alternating trill; grade 4 reports that the task was unavailable, without claiming it was performed. MIDI recognizes rating commands only; it does not certify performance or record playing telemetry.

This protocol differs from the calculator's historical `exploratory-fixed-frame-protocol-v1`, whose trill retained a held reference finger. The viewer does not create calculator sessions or observations for the new task. `calibration-pilot-v1.json` keeps its original bytes, identity, instructions and evidence. Legacy `calibration.json` also remains separate. The new additive file does not affect scores, edited fingers, practice progress, settings or calculated costs. Exporting historical evidence must retain its original protocol rather than reclassifying it.

The public, pinned calculator supplies bounded **contact templates only**: 208 Jankó targets in eight blocks, or 52 conventional targets in four blocks. The new collection records their calculator package, revision, template protocol and complete nominal geometry identity. Targets cover thumb–index and index–middle, both reference roles, distances 1–13 chromatic steps, and both actual Jankó copies. Each instrument has one collection with canonical right-hand identities. The selected performing hand is recorded with each setup and report; changing hand requires a fresh setup acknowledgment without creating a second collection.

The canonical central reference is MIDI 60. Jankó left-hand realization reflects pitch as `120 − pitch`, retaining physical row and level. Conventional left-hand realization uses MIDI 64 as its reference and reflects pitch as `124 − pitch`. The latter maps C's right-side rear cutout onto E's left-side cutout. Before supplying targets, the viewer verifies the reflected **usable and body patches**, depths, resting/held heights and rows for every target; conventional key colors must also match. Jankó paint colors identify pitches rather than different physical shapes. A missing or incompatible contact rejects collection creation rather than inventing an unavailable grade.

The player acknowledges a relaxed reference setup once per block and after a break, reopening or hand change. `effortSetupInstruction(trial)` inserts the actual plain finger names into the protocol's setup template. The setup page displays this instruction and each saved acknowledgment retains that exact text. Archive validation resolves the first physical trial of the acknowledged block for the recorded performing hand and checks the text against the same helper. Wrist position and hand direction remain fixed. The reference finger keeps its contact point between targets while both fingers participate in the trill. The other finger may bend, extend or spread and choose its tested depth at the horizontal usable center. No wrist pose, finger anatomy or exact front-to-back contact coordinate is inferred.

The archive retains append-only setups, reports and retractions. Corrections add reports; progress uses the latest unretracted report for each canonical target. Every report records its actual hand, exact physical reference/other key identities, setup index, distinct protocol, ordinal grade and sanitized manual/MIDI rating command. Unknown is never grade 4. Finishing the finite queue proves its coverage, not a fitted hand model or an interpolation rule.

All durable mutations write a complete candidate before publishing advancement. Pending writes gate further commands. Failure retains the prior accepted snapshot and draft notes. Closing exposes a flush barrier so reopening cannot race an earlier write. Runtime held-control and MIDI edge state is not persisted. Opening or breaking clears setup readiness in memory without rewriting historical records. Invalid or unsupported bytes remain read-only and export losslessly in a base64 envelope; read failures also prevent replacement.
